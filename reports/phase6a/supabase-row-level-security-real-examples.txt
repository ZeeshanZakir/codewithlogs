## What RLS should enforce
A query filter in a React component is a convenience, not an access boundary.
This example requires user A to read and edit A's notes while user B cannot access
them, even through direct API requests. It intentionally has no administrator
flag, team role, recursive membership helper or privileged browser key.

RLS controls which rows an ordinary role can use. Object and column privileges
also matter. A request can fail because a grant is missing before its row policy
is relevant. Conversely, a broad grant alone does not supply the required policy.
An enabled table with no applicable policy normally denies row access for roles
subject to RLS. Owners/superusers/BYPASSRLS roles have special behavior; test the
application's real role rather than assuming the SQL editor proves protection.

## Complete own-row schema and privileges
Apply the following only in an approved empty disposable Supabase project, as a
trusted setup owner. It creates separate teaching tables, not a production migration.

```sql
-- DRAFT, NOT EXECUTED. Empty disposable Supabase project only.
begin;
create table public.cwl_rls_notes (
  id uuid primary key default gen_random_uuid(),
  owner_id uuid not null default auth.uid() references auth.users(id),
  body text not null check (char_length(body) between 1 and 1000)
);
create index cwl_rls_notes_owner_idx on public.cwl_rls_notes(owner_id);
alter table public.cwl_rls_notes enable row level security;
revoke all on public.cwl_rls_notes from public, anon, authenticated;
grant select, delete on public.cwl_rls_notes to authenticated;
grant insert (body), update (body) on public.cwl_rls_notes to authenticated;
create policy cwl_notes_read on public.cwl_rls_notes for select to authenticated
  using ((select auth.uid()) = owner_id);
create policy cwl_notes_insert on public.cwl_rls_notes for insert to authenticated
  with check ((select auth.uid()) = owner_id);
create policy cwl_notes_update on public.cwl_rls_notes for update to authenticated
  using ((select auth.uid()) = owner_id)
  with check ((select auth.uid()) = owner_id);
create policy cwl_notes_delete on public.cwl_rls_notes for delete to authenticated
  using ((select auth.uid()) = owner_id);
commit;
```

For this sample, INSERT accepts body only. owner_id is assigned from auth.uid().
UPDATE can change body only. A client cannot promote itself or transfer ownership
by including another column. Existing broad grants must be inspected when adapting
the example: adding a narrow column grant does not undo a separate broad grant.
Table-level REVOKE also does not remove pre-existing column grants. Inspect both
levels and inherited role privileges before adapting this to an existing table.
The example is intentionally for a newly created, empty teaching table.

USING determines which existing rows qualify. WITH CHECK constrains the proposed
row on INSERT/UPDATE. PostgreSQL has fallback behavior when some clauses are
omitted: when an applicable UPDATE policy omits WITH CHECK, its USING expression
can also constrain the proposed row. Omitting the clause is not automatically a
policy bypass. Writing both makes this example's ownership rule explicit.
An update path also needs the relevant row visibility/SELECT policy and privileges.

## Use a real application identity
With the authenticated browser/SSR client for A, a minimal call is:

```js
const { data, error } = await supabase
  .from('cwl_rls_notes')
  .insert({ body: 'Check the owner boundary' })
  .select('id, body')
  .single();
if (error || !data) throw new Error('Note could not be created');
// Use data.id in the application; do not log private row content.
```

This snippet assumes a correctly configured authenticated client; it is not a
full sign-in flow. Keep private keys and raw provider errors out of browser logs.
Use the public application key with a user's session. A service-role test can
bypass the boundary you intended to verify.

## Expected results and the required test matrix
These are acceptance criteria, not captured database results:
- Anonymous SELECT/INSERT/UPDATE/DELETE: denied by the specified grants.
- A inserts body, then reads/updates/deletes A's row: allowed within constraints.
- B selecting A's ID: no visible row. Updating/deleting it: zero affected rows.
- A inserting an owner_id or updating it: denied by column privileges.
- A body longer than 1,000 characters or empty body: constraint failure.

Check data, error and affected rows. A policy-filtered SELECT can return an empty
array without an error; that is not proof the row is absent. Test each operation
directly through the API as A and B, then confirm the unchanged row using the
authorized owner. Do not log in as an administrative database role and call it
an authenticated API test. Record each identity, operation, HTTP status, error code, affected rows and
owner reread. A successful HTTP response with zero rows is not a successful edit.
For a reproducible sequence, have A create a note and retain its ID; sign in as B
and request that ID through SELECT, UPDATE with a returned-row selection, and
DELETE with a returned-row selection. Then sign back in as A and verify the note
is unchanged. Repeat without a user session. These are pending tests.

## Diagnose “new row violates row-level security policy”
Record the table, requested operation, whether a session is attached and the
policy's role/expressions. Compare the resulting row with WITH CHECK. Also inspect
object grants and defaults. Do not disable RLS, add USING(true) everywhere or use
a service-role key in a browser to make the request pass.

For updates, inspect both old-row visibility and new-row checks. A zero-row update
may indicate a hidden row, wrong ID or concurrent change. Reread with the correct
identity and select the affected rows deliberately instead of claiming success
because error is null.

## Avoid recursive and role-escalation helpers
A profiles policy that queries profiles again can recurse. That does not justify
adding an unrestricted definer function to an exposed schema. Review the actual
policy graph and move authorization data to a deliberate controlled design where
appropriate. Any definer helper needs a trusted owner, fixed name resolution,
narrow EXECUTE grants and tests for unauthorized arguments. No such helper is
included or claimed tested in this guide.

A writable is_admin or role field is an authorization problem even if its row is
owned by the user. Keep privileged assignments out of ordinary update grants and
client-editable metadata. Verify attempted escalation through the API.

## Review all policies together
Permissive policies combine with OR. Adding a permissive allow-all rule can undo
a restrictive-looking example. Restrictive policies further constrain applicable
permissive policies; they do not independently create access. Inspect all policies,
role memberships, grants, exposed views and functions before making a security claim.
No performance improvement or administrator-proof guarantee is established here.
