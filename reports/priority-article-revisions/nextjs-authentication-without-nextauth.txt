## Scope and security boundary
This is a separate educational Supabase example, not a migration of CodeWithLogs.
The website continues to use its existing NextAuth configuration and MongoDB CMS.
Its admin authentication is not replaced or weakened by this fixture.

The example pins Next.js 16.2.6, React 19.2.4, @supabase/ssr 0.12.7 and
@supabase/supabase-js 2.118.0 in fixtures/priority-articles/package-lock.json.
Use the recorded test environment/results rather than inferring support for an
untested OS or dependency combination. The whole guide remains DRAFT: no live
Supabase sign-in, refresh-token rotation, two-user RLS or logout run has occurred.

Authentication proves identity; authorization decides which data/actions that
identity may access. A layout check can improve navigation but cannot secure
every Server Action, Route Handler or data-access entry point. This revision
performs checks at each protected operation and adds database RLS as another layer.

## 2. Provide both clients and the full refresh helper
The browser client is separate from the server client. The server awaits cookies;
writable actions/handlers must propagate cookie-write errors rather than silently
swallowing them. Server Components use the read-only path and depend on Proxy to
refresh/write cookies before rendering.

File: src/lib/supabase/config.ts
```ts
export function supabaseConfig() {
  const url = process.env.NEXT_PUBLIC_SUPABASE_URL;
  const key = process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY;
  if (!url || !key) throw new Error("Supabase public configuration is missing.");
  return { url, key };
}
```

File: src/lib/supabase/server.ts
```ts
import "server-only";
import { createServerClient } from "@supabase/ssr";
import { cookies } from "next/headers";
import { supabaseConfig } from "./config";

export async function createClient(writable = false) {
  const cookieStore = await cookies();
  const { url, key } = supabaseConfig();
  return createServerClient(url, key, {
    cookies: {
      getAll: () => cookieStore.getAll(),
      setAll(values) {
        if (writable) {
          values.forEach(({ name, value, options }) => cookieStore.set(name, value, options));
          return;
        }
        // Server Components cannot set cookies. Proxy performs refresh before rendering.
        // Writable actions/handlers pass true so write errors are never swallowed there.
      },
    },
  });
}
```
File: src/lib/supabase/proxy.ts
```ts
import { createServerClient } from "@supabase/ssr";
import { NextResponse, type NextRequest } from "next/server";
import { supabaseConfig } from "./config";

export async function updateSession(request: NextRequest) {
  let response = NextResponse.next({ request });
  const { url, key } = supabaseConfig();
  const supabase = createServerClient(url, key, {
    cookies: {
      getAll: () => request.cookies.getAll(),
      setAll(values, headers) {
        values.forEach(({ name, value }) => request.cookies.set(name, value));
        response = NextResponse.next({ request });
        values.forEach(({ name, value, options }) => response.cookies.set(name, value, options));
        Object.entries(headers).forEach(([name, value]) => response.headers.set(name, value));
      },
    },
  });
  // This example deliberately requests the current server-confirmed user.
  // getClaims is another verified-token option; getSession alone is insufficient.
  await supabase.auth.getUser();
  response.headers.set("Cache-Control", "private, no-cache, no-store, must-revalidate, max-age=0");
  response.headers.set("Expires", "0");
  response.headers.set("Pragma", "no-cache");
  return response;
}
```
File: src/proxy.ts
```ts
import type { NextRequest } from "next/server";
import { updateSession } from "@/lib/supabase/proxy";

export function proxy(request: NextRequest) {
  return updateSession(request);
}

export const config = { matcher: ["/dashboard/:path*", "/api/private/:path*", "/login", "/logout"] };
```

Return the response carrying refreshed cookies. Replacing it with an unrelated
response can lose the session. Restrict the matcher to routes using auth and do
not cache responses containing session cookies in a shared public cache. This
example marks its proxy response private/no-store and does not redirect there.
Protected operations still verify identity themselves.

This example deliberately calls getUser to obtain a fresh server-confirmed user.
Current Supabase guidance also offers getClaims for verified-token identity,
depending on key configuration; it is inaccurate to say getUser is the only valid
verification method forever. getSession's embedded user alone is not sufficient
for authorization. Token expiry is configurable, not universally exactly one hour.
Next.js 16 uses proxy.ts; explain middleware.ts separately for older releases.

## 3. Validate credentials and keep redirects fixed
Do not trust FormData casts or display raw provider/internal errors in URLs.
These actions validate presence/types, use a fixed destination and give a generic
failure code. A production authentication surface also needs abuse controls and
appropriate account confirmation/recovery workflows.

File: src/app/login/actions.ts
```ts
"use server";

import { redirect } from "next/navigation";
import { createClient } from "@/lib/supabase/server";

export async function login(form: FormData) {
  const email = form.get("email");
  const password = form.get("password");
  if (typeof email !== "string" || typeof password !== "string" || !email.trim() || !password) {
    redirect("/login?error=invalid-input");
  }
  const client = await createClient(true);
  const { error } = await client.auth.signInWithPassword({ email: email.trim(), password });
  if (error) redirect("/login?error=sign-in-failed");
  redirect("/dashboard");
}

export async function logout() {
  const client = await createClient(true);
  const { error } = await client.auth.signOut();
  if (error) throw new Error("Sign-out failed.");
  redirect("/login");
}
```

## 4. Protect data and mutations at the boundary
The guard checks the provider result and fails closed when an error accompanies
a user. A forged hidden user_id never chooses the insert owner. The server uses
the authenticated identity; the read query also scopes by that identity. No service
role key is used to bypass RLS. A logged-in page is not itself an authorization test.

File: src/lib/authorization.ts
```ts
export type IdentityClient = {
  auth: { getUser(): Promise<{ data: { user: { id: string } | null }; error: unknown }> };
};

export class AuthenticationRequired extends Error {}

export async function requireUser(client: IdentityClient) {
  const { data, error } = await client.auth.getUser();
  if (error || !data.user) throw new AuthenticationRequired("Authentication required.");
  return data.user;
}
```
File: src/lib/notes.ts
```ts
import "server-only";
import { createClient } from "@/lib/supabase/server";
import { requireUser } from "@/lib/authorization";

export async function readOwnNotes() {
  const client = await createClient();
  const user = await requireUser(client);
  const { data, error } = await client.from("notes").select("id, body").eq("user_id", user.id);
  if (error) throw new Error("Notes could not be loaded.");
  return data as { id: string; body: string }[];
}
```
File: src/app/dashboard/actions.ts
```ts
"use server";

import { revalidatePath } from "next/cache";
import { createClient } from "@/lib/supabase/server";
import { requireUser } from "@/lib/authorization";

export async function addNote(form: FormData) {
  const client = await createClient(true);
  const user = await requireUser(client);
  const body = form.get("body");
  if (typeof body !== "string" || !body.trim() || body.length > 2000) {
    throw new Error("Enter a note between 1 and 2000 characters.");
  }
  const { error } = await client.from("notes").insert({ user_id: user.id, body: body.trim() });
  if (error) throw new Error("Note could not be saved.");
  revalidatePath("/dashboard");
}
```

File: src/app/api/private/route.ts
```ts
import { AuthenticationRequired, requireUser } from "@/lib/authorization";
import { createClient } from "@/lib/supabase/server";

export async function GET() {
  try {
    const client = await createClient(true);
    const user = await requireUser(client);
    return Response.json({ userId: user.id }, { headers: { "Cache-Control": "private, no-store" } });
  } catch (error) {
    if (error instanceof AuthenticationRequired) return Response.json({ error: "Authentication required." }, { status: 401 });
    return Response.json({ error: "Authentication unavailable." }, { status: 503 });
  }
}
```
File: schema.sql
```sql
-- Run ONLY in an approved disposable Supabase project; never the blog database.
create table public.notes (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id),
  body text not null check (char_length(body) between 1 and 2000)
);
alter table public.notes enable row level security;
revoke all on public.notes from anon, authenticated;
grant select, insert on public.notes to authenticated;
create policy "read own notes" on public.notes for select to authenticated
using ((select auth.uid()) = user_id);
create policy "insert own notes" on public.notes for insert to authenticated
with check ((select auth.uid()) = user_id);
```

The schema intentionally grants only the sample operations. It does not silently
grant updates/deletes or implement admin roles. Extending those capabilities needs
separate policies and negative tests. The SQL has not been run in a live project.

## 5. Reproduce the unsafe assumption and verify the replacement
The original assumption was that protecting a parent layout was enough. A direct
request to a Route Handler or invocation of a Server Action must be checked even
if the UI hides it. Run node scripts/test-priority-articles.mjs. It exercises the
actual guard/action/data modules with mocked identity/data transports: anonymous
calls fail before a write/query, a forged form owner is ignored, reads use the
authenticated owner and an identity error prevents a mutation. The real local
Next/Supabase SDK route is separately requested without a session and must return
401; /dashboard redirects to /login. No test account or database record is created.

These are limited application-boundary tests. Mocked identities do not prove JWT
validation, and a no-session SDK response does not prove token refresh or RLS.
Do not label this guide verified based on those checks alone.
