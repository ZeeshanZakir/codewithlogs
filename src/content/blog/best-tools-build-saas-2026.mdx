The first SaaS I tried to build took me four months to launch. Half of that time wasn't spent building the actual product — it was spent figuring out which tools to use, getting them connected, and debugging the integration between them.

The second SaaS took three weeks to launch. The difference wasn't that I worked harder. It was that I had already made all the tool decisions.

Choosing your stack before you build is one of the highest-leverage decisions in a SaaS project. The right tools disappear into the background and let you focus on product. The wrong ones become their own full-time job.

Here's what I'd use today if I was starting from scratch.

## Frontend — Next.js

There's not much debate here for a JavaScript developer. Next.js 15 is the best framework for building SaaS products right now. It handles routing, server rendering, API routes, and static generation in one package. Vercel (the company behind Next.js) has made the developer experience excellent.

The App Router in Next.js 15 is particularly good for SaaS because the layout system makes it easy to have separate layouts for marketing pages, authenticated dashboard pages, and admin areas — each with their own navigation and styling.

## Authentication — Clerk or NextAuth

Authentication is one of those things that sounds simple and is actually treacherous to build yourself. Password hashing, session management, email verification, password reset flows, OAuth providers, token refresh logic — there's a lot that can go wrong.

**Clerk** is my current recommendation for new SaaS projects. It's a hosted authentication service with pre-built React components. You drop in a `<SignIn />` component and authentication works. Social login, magic links, multi-factor authentication, user management — all included. Free up to 10,000 monthly active users, which covers you through early traction.

**NextAuth v5** (now called Auth.js) is the free self-hosted alternative. More control, no usage-based pricing, but you're responsible for the implementation. I use this on projects where Clerk's pricing would become significant at scale.

## Database — Supabase or MongoDB Atlas

This depends on your data model.

If your product has mostly relational data — users, organizations, subscriptions, and records with clear relationships — **Supabase** is my recommendation. It's hosted PostgreSQL with a generous free tier, a nice dashboard UI, real-time subscriptions, and Row Level Security for protecting user data. The JavaScript SDK is intuitive and well-documented.

If you're building with flexible, document-style data that doesn't fit neatly into tables — or if you're already comfortable with MongoDB from a MERN background — **MongoDB Atlas** is excellent. The free M0 cluster is enough to get through development and early users.

Pick based on your data, not on which logo looks cooler.

## Payments — Stripe

Stripe is the default choice for good reason. The documentation is the best in the industry. The JavaScript SDK works beautifully with Next.js. And the Stripe dashboard is genuinely useful for monitoring revenue, managing subscriptions, and handling refunds.

For a SaaS with subscription billing, you'll specifically want Stripe's Billing product. Set up your Products and Prices in the Stripe dashboard, use Stripe Checkout for the payment flow, and listen to webhooks for subscription events (created, updated, cancelled).

Stripe takes 2.9% + $0.30 per transaction. That's the industry standard. If you're in a market where Stripe isn't available, Paddle is a strong alternative that also handles international tax compliance.

## Email — Resend

Email in SaaS covers transactional emails (welcome messages, password resets, receipts) and marketing emails (newsletters, announcements, re-engagement).

**Resend** has become my go-to for transactional email. It has a clean API, a React Email library for building email templates in JSX (which is delightful), and excellent deliverability. Free tier includes 3,000 emails per month.

For marketing email once you grow a list, **ConvertKit** (now called Kit) or **Loops** work well with SaaS products specifically.

## Hosting — Vercel

For a Next.js SaaS, Vercel is the simplest deployment story. Connect your GitHub repository, configure environment variables, and every push to main deploys automatically. Preview deployments for every pull request. Global CDN. Serverless functions for API routes.

The free Hobby tier works for development and small products. The Pro tier at $20/month adds more function execution time, higher bandwidth limits, and team features.

For background jobs, cron tasks, or heavier server workloads that don't fit Vercel's serverless model, **Railway** is a good complement — easy to use and reasonably priced.

## Real-Time Features — Pusher or Supabase Realtime

If your SaaS needs real-time updates — live notifications, collaborative editing, live dashboards — you need a WebSocket solution.

**Supabase Realtime** is the simplest option if you're already using Supabase. It streams database changes directly to your frontend clients.

**Pusher** is a good hosted option for more custom real-time event broadcasting, especially if you're not using Supabase.

## File Storage — Cloudflare R2 or AWS S3

If your SaaS handles file uploads — profile photos, documents, exports, images — you need object storage.

**Cloudflare R2** is my first choice right now because it has no egress fees. AWS S3 charges you every time someone downloads a file from it, which adds up fast. R2 stores the same data without the egress cost. The API is S3-compatible so most S3 SDKs work with it.

## The Stack Summary

If I was starting a new SaaS project today:
- **Framework:** Next.js 15
- **Auth:** Clerk (or NextAuth for full control)
- **Database:** Supabase (relational) or MongoDB Atlas (document)
- **Payments:** Stripe
- **Email:** Resend
- **Hosting:** Vercel
- **Storage:** Cloudflare R2

That stack can take you from zero to a production SaaS serving real paying customers without any infrastructure management headaches. All of these services have free tiers that cover early development and initial users.

The goal of choosing tools is to minimize the time you spend thinking about infrastructure and maximize the time you spend building the thing users actually pay for.
